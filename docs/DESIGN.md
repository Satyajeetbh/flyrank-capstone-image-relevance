# System Design Document

FlyRank AI Image Understanding & Content Matching Engine

## 1. System Architecture & Layers

The system is organized into decoupled, unidirectional layers built with Node.js, TypeScript, Express, PostgreSQL with pgvector, and Redis with BullMQ.

```text
       ┌────────────────────────────────────────────────────────┐
       │                   API Layer (src/api)                  │
       │   POST /images  │  GET /posts/:id/images  │  /suggestions │
       └───────────────────────────┬────────────────────────────┘
                                   │
       ┌───────────────────────────▼────────────────────────────┐
       │              Application Layer (src/application)       │
       │   Image Processing │ Semantic Retrieval │ Review Service │
       └─────────────┬─────────────────────────────┬────────────┘
                     │                             │
       ┌─────────────▼───────────────┐ ┌───────────▼────────────┐
       │   Domain Layer (src/domain)  │ │ Providers (src/providers)│
       │ Mismatch Guard │ Guard Policy│ │ Local/OpenAI Vision    │
       │ Schemas │ AI Usage & Budget  │ │ Gemini/OpenAI Embedding│
       └─────────────┬───────────────┘ └───────────┬────────────┘
                     │                             │
       ┌─────────────▼─────────────────────────────▼────────────┐
       │            Repositories Layer (src/repositories)       │
       │   images, image_metadata, embeddings, suggestions...   │
       └───────────────────────────┬────────────────────────────┘
                                   │
       ┌───────────────────────────▼────────────────────────────┐
       │          Infrastructure Layer (src/infrastructure)     │
       │        PostgreSQL 16 (pgvector)  │  Redis 7 (BullMQ)   │
       └────────────────────────────────────────────────────────┘
```

- **API Layer (`src/api`)**: Minimal Express 5 router layer handling HTTP request parsing, Zod transport validation, status mapping, and JSON response delivery.
- **Application Layer (`src/application`)**: Use-case orchestration linking domain rules, repositories, queues, and provider interfaces without coupling to specific transport or database drivers.
- **Domain Layer (`src/domain`)**: Core business rules, Zod domain contracts, mismatch guard logic, threshold policies, and error classifications. Completely free of external vendor SDKs and database dependencies.
- **Providers Layer (`src/providers`)**: External AI integrations for vision understanding and text embeddings conforming to domain-defined interfaces.
- **Repositories Layer (`src/repositories`)**: Explicit, parameterized SQL data-access objects backed by the shared PostgreSQL connection pool.
- **Infrastructure Layer (`src/infrastructure`)**: Connection management for PostgreSQL (`pg.Pool`) and Redis (`ioredis`), plus BullMQ queue configuration.
- **Workers Layer (`src/workers`)**: Asynchronous BullMQ background worker consuming image processing jobs outside the HTTP request lifecycle.

## 2. PostgreSQL + pgvector Persistence

The storage foundation uses PostgreSQL 16 with the `pgcrypto` and `vector` (pgvector) extensions.

Database migrations reside in `migrations/` and run in numeric sequence:
1. `001_enable_extensions.sql`: Enables `pgcrypto` for UUID generation and `vector` for embedding columns.
2. `002_create_core_tables.sql`: Creates core tables with constraints:
   - `images`: Image ingestion tracking (`source_url`, `storage_reference`, `processing_status`).
   - `image_metadata`: Validated structured vision attributes (`subject`, `category`, `attributes` JSONB, `caption`, `vision_confidence`).
   - `image_embeddings`: 1536-dimensional vectors with `(image_id, embedding_model)` uniqueness.
   - `posts`: Blog post content with expected subjects and categories.
   - `post_embeddings`: 1536-dimensional vectors with `(post_id, embedding_model)` uniqueness.
   - `suggestions`: Candidate matches generated by semantic retrieval with `guard_status` (`accept`, `reject`, `review`), `similarity_score`, and machine-readable `reason`.
   - `reviews`: Human review records (`approved`, `rejected`, `needs_review`) with reviewer identifier and audit trail.
   - `ai_usage`: Fine-grained token usage and estimated monetary cost logs per operation.
   - `jobs`: PostgreSQL background job status tracking (`queued`, `running`, `completed`, `failed`).
3. `003_create_indexes.sql`: Foreign keys, status filters, timestamp sorting, and similarity score ordering indexes.

Vector storage uses `vector(1536)`. Similarity search evaluates exact cosine distance using the pgvector `<=>` operator:
$$\text{similarity} = 1 - (\text{embedding} \Leftrightarrow \text{query\_vector})$$

## 3. Image Metadata Flow

Image ingestion separates synchronous acceptance from asynchronous analysis:

```text
POST /images (URL, storageReference)
       │
       ├─► Validate input with Zod
       ├─► Create image record (processing_status = 'pending')
       ├─► Create PostgreSQL job record & enqueue BullMQ job
       └─► Return HTTP 201 Created (Image & Job descriptor)
              │
              ▼ (Asynchronous BullMQ Worker)
       ├─► Update job status to 'running'
       ├─► VisionProvider.analyzeImage(sourceUrl)
       ├─► Validate output against imageMetadataSchema
       ├─► Persist structured metadata to image_metadata table
       ├─► Generate text representation and embed via EmbeddingProvider
       ├─► Persist 1536-d vector to image_embeddings
       ├─► Update images.processing_status to 'completed'
       └─► Mark job 'completed'
```

The validated metadata schema enforces:
- `subject` (string, non-empty)
- `category` (controlled taxonomy: animal, food, landscape, object, vehicle)
- `attributes` (array of string descriptors)
- `caption` (descriptive natural-language summary)
- `visionConfidence` (numeric float constrained between 0.0 and 1.0)

## 4. AI Provider Boundaries

The system defines swappable, vendor-neutral provider interfaces:

### Vision Provider (`VisionProvider`)
- **`analyzeImage(url: string): Promise<ImageMetadata>`**
- **`LocalVisionProvider` (`VISION_PROVIDER=local`)**: Submission-safe default. Loads pre-generated, Zod-validated metadata fixtures from `data/corpus/metadata/`. Requires zero API keys and zero cost, guaranteeing reproducible evaluation.
- **`OpenAIVisionProvider` (`VISION_PROVIDER=openai`)**: Production vision implementation querying `gpt-4.1-mini` via the OpenAI Responses API using structured JSON Schema output. Classifies network/timeout failures as retryable `provider_api_failure` while schema mismatches fail permanently.

### Embedding Provider (`EmbeddingProvider`)
- **`embedText(text: string): Promise<number[]>`**
- **`GeminiEmbeddingProvider` (`EMBEDDING_PROVIDER=gemini`)**: Default submission embedding provider using `@google/genai` and `gemini-embedding-2`. Returns 1536-dimensional vectors matching the PostgreSQL column schema.
- **`OpenAIEmbeddingProvider` (`EMBEDDING_PROVIDER=openai`)**: Alternative provider using OpenAI `text-embedding-3-small` producing 1536-dimensional vectors.

## 5. Embedding Flow

Embeddings represent the semantic content of both blog posts and images in a shared 1536-dimensional vector space:

1. **Image text representation**: Composed deterministically from validated metadata:
   ```text
   subject: <subject>
   category: <category>
   attributes: <attr1>, <attr2>...
   caption: <caption>
   ```
2. **Embedding generation**: Passed to `EmbeddingProvider.embedText()`, producing a 1536-dimensional unit vector.
3. **Post embedding**: Blog post `title` and `content` are formatted and embedded through the same embedding model.
4. **Persistence**: Vectors are persisted into `image_embeddings` and `post_embeddings` with explicit model attribution (`gemini-embedding-2` or `text-embedding-3-small`).

## 6. Deterministic Mismatch Guard

The deterministic mismatch guard (`src/domain/mismatch-guard.ts`) prevents semantically plausible but factually incorrect matches from being accepted automatically.

### Thresholds (`src/domain/guard-policy.ts`)
- **Semantic similarity threshold**: `0.50` (calibrated for Gemini Embedding 2 on the 50-image corpus).
- **Vision confidence threshold**: `0.70`.

### Guard Logic
The guard evaluates:
1. **Semantic similarity**: Must meet or exceed the similarity threshold (`0.50`). Candidates below threshold produce `NO_CONFIDENT_MATCH` with reason code `LOW_SIMILARITY`.
2. **Vision confidence**: Must meet or exceed confidence threshold (`0.70`). Low vision confidence routes the candidate to `REVIEW` with `LOW_VISION_CONFIDENCE`.
3. **Category match**: Candidate image category must align with expected post category. Category conflicts produce `REJECT` with `CATEGORY_MISMATCH`.
4. **Subject match**: Candidate image subject must align with expected post subject. Severe subject mismatches (e.g. gray wolf for red fox post) produce `REJECT` with `SUBJECT_MISMATCH`.

### Decision Outcomes
- **`ACCEPT`**: High similarity, high vision confidence, verified subject and category. Recommended to user.
- **`REVIEW`**: Moderate similarity or borderline confidence requiring human approval.
- **`REJECT`**: Explicit contradiction in subject, category, or sub-threshold similarity.
- **`NO_CONFIDENT_MATCH`**: Returned explicitly when all candidates are rejected or below threshold, rather than forcing the least-bad image.

## 7. Semantic Retrieval Flow

The retrieval workflow (`src/application/semantic-image-retrieval.ts`) powers `GET /posts/:id/images`:

```text
GET /posts/:id/images
       │
       ├─► Fetch post and post embedding from post_embeddings
       ├─► Execute pgvector cosine distance query against image_embeddings
       ├─► Join candidate images with image_metadata
       ├─► Evaluate candidates with evaluateMismatchGuard()
       ├─► Persist suggestion row in suggestions table (with score & guard status)
       └─► Return JSON matching result:
             - match: ImageCandidate | null
             - status: 'ACCEPT' | 'REVIEW' | 'NO_CONFIDENT_MATCH'
             - confidence: number
             - reason: string
```

## 8. BullMQ Background Processing

Expensive AI operations (vision analysis, embedding calculation) run outside the synchronous request path via Redis and BullMQ:

- **Queue**: `image-processing` queue instantiated via `src/infrastructure/image-processing-queue.ts`.
- **Worker**: `src/workers/image-processing-worker.ts` with graceful startup and shutdown hooks.
- **Failure Classification (`src/domain/job-errors.ts`)**:
  - `isRetryableJobError`: Network timeouts, rate limits (`429`), and provider API 5xx errors trigger BullMQ exponential backoff retries.
  - Non-retryable errors (malformed images, Zod validation errors, schema violations) terminate the job immediately with status `failed`, avoiding wasteful API costs.

---

## 9. Review / Suggestion Workflow

Human-in-the-loop oversight is supported through suggestions and reviews (`src/application/suggestion-review.ts`):

- Retrieval suggestions are persisted to `suggestions` with `guard_status` (`accept`, `review`, `reject`).
- Review Endpoints:
  - **`GET /suggestions/:id`**: Returns suggestion details, related post, and image metadata.
  - **`POST /suggestions/:id/approve`**: Validates reviewer body `{ reviewer, reason? }`, transitions suggestion to approved state, and inserts an audit row in `reviews`.
  - **`POST /suggestions/:id/reject`**: Validates reviewer body `{ reviewer, reason }`, records rejection in `reviews`, and flags the suggestion as rejected.

## 10. Evaluation & Threshold Calibration

The evaluation harness measures retrieval quality without live external API costs:

- **Labeled Dataset (`data/evaluation/labeled-posts.json`)**: 10 ground-truth pairs mapping post IDs to expected corpus image storage references.
- **Retrieval Evaluator (`scripts/evaluate-retrieval.mjs`)**:
  - Baseline top-1 accuracy (unguarded vector nearest-neighbor).
  - Guarded top-1 accuracy (with deterministic mismatch guard).
  - Accepted incorrect matches (target: 0).
  - False rejections and `NO_CONFIDENT_MATCH` count.
- **Threshold Calibration (`--calibrate`)**: Performs parametric sweeps over similarity thresholds ($0.50$ to $0.70$) to evaluate precision-recall trade-offs and empirically justify the chosen production policy.

---

## 11. AI Usage & Cost Tracking

All external AI operations are metered and cost-controlled:

- **Audit Table (`ai_usage`)**: Captures `entity_type`, `entity_id`, `operation`, `provider`, `model`, `input_units`, `output_units`, `estimated_cost`, and `status`.
- **Pricing Configuration (`src/domain/ai-usage.ts`)**: Encodes token unit costs for OpenAI vision and embedding models. Gemini Embedding 2 runtime currently reports zero token usage units via SDK and is recorded with documented `$0` estimated cost.
- **Budget Ceiling (`AI_USAGE_BUDGET_USD`)**: Checked by `assertAiBudget()` before dispatching external calls. If accumulated spend meets or exceeds the safety budget (default `$1.00`), calls are rejected to prevent unexpected billing spikes.
